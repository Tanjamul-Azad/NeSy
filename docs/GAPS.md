# CREST — Live Gap & Edge Register

**This file exists so nothing hides.** Every open gap, every assumption we
have not verified, every edge we have not checked, and every claim we have
already had to retract — in one place, with a definite "what closes it" for
each. If a gap is not in here, it is not being tracked; if it is in here and
marked OPEN, no downstream claim may quietly assume it is closed.

**Rules for this file (agreed 2026-08-22):**
1. A gap closes only when its stated close-condition is *met and pointed at*
   (a file, a number, a commit) — never because it feels handled.
2. Anything discovered mid-work gets added here immediately, in the same
   session, even if it is inconvenient.
3. Section D (retracted claims) never shrinks. Corrections stay visible.
4. Status vocabulary: **OPEN** / **IN PROGRESS** / **CLOSED** / **ACCEPTED
   LIMITATION** (won't fix, stated in the paper instead).

Last updated: 2026-08-27.

**Every item below is assigned to a stage in `docs/FYDP2_PLAN.md`** — the single plan of record. An item with no stage is a planning bug, not an untracked task.

| **E18** | **Attribution ground truth has a bootstrapping dependency not yet stated in the plan.** The P-A gate is 'attribution precision vs human labels', which presupposes humans can assign attribution labels reliably. | **E19** | **"Unformalizable" is an asymmetric negative claim, and "formalizable" is not an absolute property.** A human failing to produce an admissible FOL is not evidence that none exists: the positive case is constructive (an existence witness), the negative case is not. Raised by external review 2026-08-27. | The ContractNLI ceiling numbers (0/10 literal, 6/10 charitable, 10/10 assumption-augmented) are currently described as a *formalizability ceiling*. E1 would inherit this defect and produce an uninterpretable number. | Freeze an operational definition BEFORE any data collection: Formalizable(x; PHI, C) relative to target formalism PHI and an explicit admissible-translation contract C. Preregistration: `docs/PREREG_E1_formalizability.md`. | **OPEN - blocks E1 data collection** |
| **E20** | **`R = (F=1 ∧ T=0)` is evaluated over ESTIMATED axes, not true ones.** The repair decision is defined on true `F`/`T` but computed from `F̂`/`T̂`, so errors on the two axes compound. Raised in-session 2026-08-27 while rewriting the S4 gate. | Without separating them, a weak attributor and a weak repair model are indistinguishable in the end-to-end number, and a failed S5 could be blamed on the wrong component. | S4 reports the achieved `R` decision quality AND an oracle-`R` upper bound computed from true axes. Both appear in the results table. | **OPEN — S4 design** |
| **E21** | **`F` may be `uncertain / not-assessable`, leaving `R` undefined.** The annotation protocol must define that value, and the deployment policy for it must be fixed in advance. | Deciding at implementation time invites choosing whichever policy flatters the results. A method abstaining on half its inputs is a different product from one abstaining on 5%, and the abstention rate is part of what is being claimed. | Preregister the policy before labels are collected — default conservative (do not repair when `F` is uncertain) — and report the abstention rate as a headline number, not a footnote. | **OPEN — blocks S3 annotation design** |
| **E22** | **Level-2 repair evaluation (semantic fidelity of the REPAIRED formula) has no assessor budgeted.** S5 needs to check that repairs preserve faithfulness, but automated fidelity signals were already measured to fail on naturalistic text (structural divergence, lift ~1.0), so this is human work absent from S3's annotation plan. | Discovering this in S5 means either skipping the check — which lets wrong-but-lucky repairs score as successes — or pausing S5 to recruit annotators. | Decide in S3: either grow the annotation scope to cover repaired-formula fidelity review, or declare in advance that level 2 is reported on a stated subsample only. | **OPEN — decide during S3** |
| **E13** | **P-C's compute resourcing decision.** Tanjamul's explicit instruction 2026-08-22: no compromise on model runs, best achievable result is required. This changes the earlier framing -- corrector model SIZE is no longer to be picked by what fits free/local hardware (RTX 4060 8GB confirmed via `nvidia-smi`; Kaggle free T4 16GB, 12h session cap). Model size should instead be an ABLATION VARIABLE (1B/3B/8B compared empirically), same discipline as the Phase 8.4 pairing ablation -- and if the best result needs full LoRA/QLoRA DPO on the 8B base without the free-tier constraints, rented cloud GPU-hours (A100/H100) is the correct resourcing, not a downsized model. | Conflating 'fits on free hardware' with 'best result' would silently cap the corrector's quality for a reason that has nothing to do with the research question -- exactly the kind of unexamined constraint this project's rigor standard exists to catch. Note: bigger model is not automatically better here either -- for this narrow, structured repair task, the DPO pairing strategy (Phase 8.1, the project's one genuine algorithmic-novelty candidate) and P-B's training-data quality plausibly matter more than raw scale, so scale must be measured, not assumed in either direction. | **Needs a cloud-compute budget figure from Tanjamul** (the OpenAI arm had an explicit $50 credit ceiling for comparison) before P-C's exact plan can be written. Once a budget exists: (1) treat corrector size as an ablation, not a foregone small-model choice; (2) run the same non-degradation and coverage gates regardless of size, so 'best result' is not used to relax the falsification discipline elsewhere in the programme. | **OPEN — awaiting budget** |

## How this file gets used

- Read section A + B at the start of any work session. If a task does not
  close a row here, ask why it is being done.
- Any new finding gets a row before the session ends, not "later".
- The paper's limitations section is written *from* B and D. Nothing in
  B or D may be omitted there.
